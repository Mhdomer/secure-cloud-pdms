# QA Audit Fixes — 2026-07-24

## Source

`docs/psm2/qa-audit-2026-07-24.md` — the full-site QA pass (26 findings
across billing/invoicing logic, a systemic frontend query bug, and UI
polish). User's explicit ask: fix everything found, not just the
critical/high items, with a strong emphasis on the invoice subsystem and
"no bugs, no endpoints open for exploitation." This document records what
was fixed, in which files, exactly how each was verified against the live
dev DB, and what's intentionally left open — same purpose and convention

**Everything below was verified against the live local `pdms` database,

browser) against real or purpose-created rows, not assumed correct from
the diff alone. One real bug (see "Bug found during verification" below)
was only caught this way.

## Fixes, by finding

### C-1 (CRITICAL) — partial payments could never be finished
**Files:** `schema.sql` (new `invoice_payments` table),
`billingController.js` (`payInvoice` rewritten, `lockInvoice` helper
added), `routes/billing.routes.js`, `BillVisitPage.tsx`,
`locales/{en,ar}/visits.json`.

Added an append-only `invoice_payments` ledger table (same pattern as
`audit_log` — `GRANT SELECT, INSERT` only, RLS mirroring `invoice_items`'
admin/doctor/patient three-way split). `payInvoice` now inserts one ledger
row per call and derives `amount_paid` as the running total instead of
overwriting it. `patient_amount` (what the patient actually owes — the
full bill, or the post-insurance co-pay) is computed once on the *first*
payment (detected via `inv.status === 'pending_billing'`, since that's
only ever true immediately before the first payment) and reused on every
later call, never recomputed. `BillVisitPage.tsx`'s gate changed from
`status !== 'pending_billing'` to also accept `'partial'`; when accepting
a repeat payment it shows "Already Collected" / "Remaining Balance", hides
the insurance detail sub-form (locked in already — see M-1), and swaps the
button label to "Collect Payment".

**Bug found during verification:** the first version of the rewritten
`UPDATE visit_invoices ... SET status=$11 ... CASE WHEN $11 = 'paid'`
query failed live with `inconsistent types deduced for parameter $11` —
the exact same Postgres quirk `visitsController.updateStatus` already has
a comment about (reusing one placeholder in both a column assignment and
a `CASE WHEN` comparison makes Postgres infer two different types for it).
Fixed by passing the status value twice, as `$11` and a new `$14`, same
fix pattern as the existing code. Caught only because payInvoice was
exercised live against the real stuck invoice below — a pure code read
would not have caught this.

**Verified live** against the exact stuck invoice from the original audit
(`06a767ab-4d7a-4e60-820a-c785bc1e1f54`, visit
`3a24445f-ff58-4594-a9aa-24defce5163e`, 4,398.75 SAR outstanding,
`patient_amount` had defaulted to 0 under the old code):
1. `/bill` page now renders the payment form instead of "not ready for
   billing" — confirmed via screenshot.
2. Collected 2000.00 cash → `amountPaid: 2000, amountBalance: 2398.75,
   status: 'partial'`.
3. Attempted 9999 (overpayment) → clean `400`: "Payment of 9999.00 exceeds
   the remaining balance of 2398.75" (this is also the H-3 verification).
4. Collected the exact remaining 2398.75 via **card** (different method
   than the first payment, on purpose — to prove mixed-method
   accumulation) → `amountPaid: 4398.75, amountBalance: 0, status: 'paid'`,
   `paidAt` set.
5. `invoice_payments` table confirmed holding both rows (2000.00/cash,
   2398.75/card) with correct timestamps.
6. `visits.status` confirmed transitioned to `'billed'`.

### C-2 (CRITICAL) — VAT hardcoded to 15%, ignoring the catalog rate
**File:** `billingController.js` (`addItem`).

`calcItem({ ..., vat_pct: 15 })` on new-item insert now reads
`svc.rows[0].vat_pct` from `clinic_services` (falling back to 15 only if
the service lookup itself came back empty, e.g. a custom/no-`service_id`
item). **Verified live**: temporarily set a real service's `vat_pct` to 0,
added it to a fresh test visit as the doctor, confirmed the response came
back `vatPct: 0, vatAmount: 0, totalWithVat` equal to the net price
(no VAT added) — then restored the service's rate to 15 immediately after.

### H-1 (HIGH) — no row locking, real race conditions
**Files:** `billingController.js` (`lockInvoice` helper; used in
`addItem`, `removeItem`, `updateQty`, `updateDiscount`, `payInvoice`;
`ensureDraftInvoice` rewritten).

Added `lockInvoice(client, invoiceId)` — a `SELECT * FROM visit_invoices
WHERE invoice_id = $1 FOR UPDATE` — called first thing in every billing
mutation. Postgres blocks a second `FOR UPDATE` on the same row until the
first transaction commits, so two concurrent mutations against the *same*
invoice now serialize instead of racing (duplicate line items, lost
updates on totals, double-processed payments). Separately,
`ensureDraftInvoice`'s bare `INSERT` (which could throw an unhandled
23505 if two near-simultaneous first-`addItem` calls for the same visit
both passed the "no existing invoice" check) is now
`INSERT ... ON CONFLICT (visit_id) DO NOTHING RETURNING invoice_id` with a
fallback `SELECT` — atomic, race-safe, no unhandled-constraint-violation
path. **Verified**: normal addItem/removeItem/updateQty/updateDiscount
flows still work correctly with the lock added (exercised live per the
C-1/C-2 verification steps above, which all go through the same locked
code paths).

### H-2 (HIGH) — no cancel/void workflow
**Files:** `schema.sql` (`visits.status` CHECK now includes `'cancelled'`),
`visitsController.js` (new `cancelVisit`), `billingController.js` (new
`cancelInvoice`), `visits.routes.js`, `billing.routes.js`,
`config/constants.js` (`CANCEL_VISIT`/`CANCEL_INVOICE` audit actions).

Two new admin/superadmin-only endpoints:
- `PATCH /visits/:visitId/cancel` — only when the visit is still
  `'waiting'` (nothing charted yet); atomically `UPDATE ... WHERE
  status='waiting'` doubles as the concurrency check, and also cancels any
  draft/pending_billing invoice tied to it.
- `PATCH /visits/:visitId/invoice/cancel` — only when the invoice is
  `draft` or `pending_billing`; refuses once any money has moved
  (partial/paid), since voiding a part-paid invoice needs an explicit
  refund decision, not something a cancel button should do silently.

**Verified live**: created a real test visit + draft invoice (the same one
used for the C-2 VAT test), cancelled the invoice (200, `{"message":
"Invoice cancelled"}`), cancelled the visit (200, status `cancelled`),
confirmed both rows show `cancelled` in the DB, confirmed a second cancel
attempt on the same visit correctly 409s ("Only a waiting visit can be
cancelled"), and confirmed a doctor-role session is correctly 403'd from
calling `cancelVisit` at all (admin/superadmin only, RBAC boundary intact).

### H-3 (HIGH) — unbounded overpayment
**File:** `billingController.js` (`payInvoice`, folded into the C-1
rewrite); `billing.routes.js` (`amount_paid` validator tightened to
`isFloat({ gt: 0 })`, was `{ min: 0 }`).

A payment that would push `amount_balance` negative is now rejected with a
`400` before anything is written (`remainingBefore + 0.01` epsilon absorbs
float/NUMERIC rounding noise without letting a real overpayment through).
**Verified live** as step 3 of the C-1 verification above (9999 against a
2398.75 remaining balance → clean 400, no DB write).

### H-4 (HIGH) — superadmin's revenue-by-department bar could exceed 100%
**File:** `billingController.js` (`getFinancialAnalytics`).

The department breakdown summed `vi.grand_total` (full billed amount,
including a `'partial'` invoice's *still-outstanding* portion) while the
top-level "Gross Revenue" summed `vi.amount_paid` (actual cash collected)
— different bases, so the department bar could read over 100% the moment
any partial payment existed in the window. Changed the department query to
sum `amount_paid` too, matching the top-level number's meaning.

### H-5 (HIGH) — medical records always show "Jan 1, 1970"
**Files:** `schema.sql` (`medical_records.updated_at` gains
`DEFAULT NOW()` + one-time backfill of existing NULL rows to their
`created_at`).

Root cause: the column had no `DEFAULT`, and while
`MedicalRecord.update()`'s `UPDATE` statement *does* correctly set
`updated_at = NOW()` (this part was already right), a record that had
**never been edited since creation** — true for essentially every seed/demo
record — had a NULL `updated_at`, which the frontend rendered as the Unix
epoch. No controller/model code change needed beyond the schema default;
`MedicalRecord.create()`'s `INSERT` doesn't list `updated_at` at all, so it
now picks up the new column default automatically. **Verified**: queried
the live DB post-fix, confirmed previously-NULL rows now show
`updated_at = created_at`.

### H-6 (HIGH) — systemic "Could not load X" on ~29 screens in dev
**Files:** `main.tsx` (`staleTime: 0` → `2000`),
`pages/patients/profile/AppointmentsTab.tsx` (date-range computed at day
granularity instead of exact milliseconds).

**Partially fixed — see honest status below.** Root cause is React 18
StrictMode's intentional dev-only double-invoke of effects colliding with
this project's global React Query config
(`refetchOnMount: 'always'`, `staleTime: 0`). Two independent
contributing factors were found and fixed:
1. `staleTime: 0` meant every remount (including StrictMode's synthetic
   second one, milliseconds after the first) was always treated as
   needing an immediate fresh fetch, racing against the first mount's
   in-flight request. Bumping to a 2-second `staleTime` is enough headroom
   for React Query to recognize the second mount's data as still fresh and
   skip the redundant/racing fetch, without meaningfully changing the
   "always basically fresh" product behavior (mutations still explicitly
   invalidate/refetch on success throughout the app, independent of
   `staleTime`).
2. `AppointmentsTab.tsx` computed its `from`/`to` query-key inputs from
   `new Date().getTime()` — exact milliseconds, different on every mount,
   including StrictMode's second pass, which defeated any deduplication
   regardless of `staleTime` (two different query keys = two genuinely
   different, independently-racing queries). Rounded to day granularity
   (same pattern `todayIso()` already uses elsewhere in the codebase) —
   this is a real improvement independent of the StrictMode question too,
   since it now actually caches across remounts instead of missing every
   time.

**Verified `staleTime` fix live** on `BillingHistoryPage` (`/billing-history`)
— reproduced the "Could not load billing history" error on a fresh page
load before the fix, confirmed it's gone (real data renders: Collected
SAR 276.00, Outstanding SAR 338.00, full invoice table) after, re-tested
twice to rule out a fluke.

**Honest gap:** `AppointmentsTab.tsx` specifically (nested inside
`PatientProfilePage`'s conditionally-rendered tab system, not a top-level
route) *still* reproduces the error even after both fixes above. This
points to a deeper parent/child remount interaction specific to how that
page's tabs conditionally mount `{currentTab === 'appointments' &&
<AppointmentsTab .../>}`, which needs more investigation than was done
here to fully resolve. **Confirmed dev-only / zero production impact**
either way — StrictMode's double-invoke only happens in development
builds; re-confirmed earlier in this same investigation by removing
`<StrictMode>` from `main.tsx` entirely as a diagnostic (reverted
immediately after, no diff left behind) and watching the error disappear
completely. If this needs to be fully silenced in dev too, the next step
is tracing exactly what remounts `PatientProfilePage`/its tab state
between StrictMode's two passes — not attempted here given this was
already a large, mostly-successful detour from the billing-subsystem work
that was the actual priority of this pass.

### M-3 (MEDIUM) — financial reports not Riyadh-anchored on explicit-date paths
**File:** `billingController.js` (`getBillingHistory`'s `from`/`to`
filters, `getFinancialAnalytics`'s explicit-`date` branch);
`billingHistory.routes.js` (added the missing `date` query validator on
`/billing/analytics` — it had none before, an unrelated small gap noticed
while fixing this).

Both now wrap the comparison in `(vi.created_at AT TIME ZONE
'Asia/Riyadh')::date` instead of a naive `created_at::date` cast against
whatever timezone the DB session happens to be in (UTC in production) —
matching the pattern `visitsController.js`'s `TODAY_START_SQL` already

branch was already correct; only the explicit-date branch had the bug.

### M-4 (MEDIUM) — currency math in unsafe JS floating point
**File:** `utils/invoiceCalc.js` (`round`).

`Math.round(n * 100) / 100` → `Math.round((n + Number.EPSILON) * 100) /
100` — the standard, minimal compensation for JS's binary floating-point
representation error at exact half-cent boundaries (e.g. `1.005 * 100 ===
100.49999999999999` uncompensated). `round` is now also exported and
reused by `billingController.js`'s `payInvoice` instead of that function
keeping its own separate `Math.round(...*100)/100` copies, so the fix
applies everywhere consistently rather than in just one place.

### M-5 (MEDIUM) — oversized dashboard photos (700KB–1.1MB PNGs for 96–544px thumbnails)
**Files:** new `real-waiting-area-thumb.jpg`, `real-general-clinic-thumb.jpg`,
`real-general-clinic-2-thumb.jpg` in `public/clinic/`; `AdminDashboard.tsx`
and `PatientDashboard.tsx` updated to reference them.

Generated properly-sized JPEG variants (resized via .NET `System.Drawing`
through PowerShell, no new npm dependency added) at roughly 2x their

`SpecialtyDetailPage.tsx`, so only new dedicated thumbnail files were
created rather than shrinking the shared master file, which would have
degraded that other, larger use case. **Verified** all three new files

dev server.

### M-6 (MEDIUM) — dashboards greet by raw login username, not real name
**Files:** `patientsController.js` (new `getMyProfile` / `GET
/patients/me`), `doctorsController.js` (new `getMyProfile` / `GET
/doctors/me`), `patients.routes.js`, `doctors.routes.js`, `lib/api.ts`
(`patientsApi.me`, `doctorsApi.me`), `DoctorDashboard.tsx`,
`PatientDashboard.tsx`.

`authStore.ts` deliberately only ever holds `userId`/`username`/`role`
(documented, intentional — see the earlier security-audit-fixes doc's
Finding 4-A discussion), so the frontend had no way to know a signed-in
doctor's or patient's actual name at all. Added two minimal, narrowly-scoped
"my profile" endpoints (patientId/doctorId derived from the session, never
a route param — same ownership pattern as `GET /billing/mine`) returning
just `fullName` (+ a couple of already-non-sensitive fields). Both
dashboards now fetch their own profile once and use `fullName`, falling
back to `username` only while loading or on error, so the header never
regresses to blank. Also fixed a third instance of the same bug: the
patient dashboard's PDF-export helper (`handleExportPdf`) was putting the
patient's national-ID username on the actual exported/printed document as
`patientName` — now uses the real name too. **Note:** admin/superadmin
dashboards were deliberately left unchanged — `users` has no `full_name`
column for staff-role accounts at all (only `doctors`/`patients` do), so
`username` is already the only, correct identifier available for those
two roles; there's no bug to fix there.

### L-4 (LOW) — stale "no RLS" comments
**Files:** `billingController.js` (`assertOwnVisit`), `visitsController.js`
(three separate comments: the walk-in `CareTeam.add` gate, `listToday`,
`updateStatus`).

All four comments asserted `visits`/`visit_invoices`/`invoice_items` "have
no RLS" as the reason the surrounding app-layer check exists. RLS was
added to those tables in a later session (schema.sql's "HIGH-03 audit
fix") after these comments were originally written — today the two layers
correctly agree (RLS + app-layer check both enforce the same boundary,
redundantly), but the stale comments were a documentation-integrity trap:
a future edit to any of this app-layer scoping logic, made by someone
trusting the comment that there's "no DB-level backstop," could diverge
from the RLS policy without anyone checking both layers together. Updated
all four to state that RLS now exists and that the app-layer check is
intentionally redundant defense-in-depth, not the sole enforcement.

### L-2 (LOW) — invoice number sequence gaps
**Not changed.** `nextval()` on `invoice_no_seq` isn't transactional in
Postgres — a rolled-back transaction (including the H-1 race this used to
enable, now closed) still burns a sequence value, leaving a permanent gap.
This is normal, expected Postgres behavior for any sequence-backed
identifier, not a bug to "fix" — noted in the original QA audit as
worth-a-note given this is a Saudi tax-invoice number specifically, not as
an action item.

## Workflow followed

Same discipline as the prior security-fixes pass
(`docs/psm2/security-audit-fixes-2026-07-24.md`), reinforced by actually
catching a real bug this time by not skipping it:

1. **Read every file involved in full before editing** —
   `billingController.js`, `visitsController.js`, `invoiceCalc.js`,
   `billing.routes.js`, `billingHistory.routes.js`, the relevant
   `schema.sql` sections, `BillVisitPage.tsx`, `InvoicePage.tsx`,
   `BillingHistoryPage.tsx`, `types/billing.ts`, `api.ts`'s billing
   section — before writing a single line of the fix, to understand the
   existing state machine, RLS boundaries, and established code patterns
   (e.g. the `$1` reused-placeholder gotcha already documented elsewhere,
   which directly predicted the bug found below).
2. **Checked live DB state before designing the ledger table** — queried
   `visit_invoices` for real stuck `'partial'` rows (found 5, one with
   4,398.75 SAR outstanding) to confirm the bug was real and currently
   affecting actual data, not just a theoretical code-read finding.
3. **Applied schema changes to the live dev DB**, not just `schema.sql` —
   same throwaway-Node-script-via-`MIGRATION_DB_USER` pattern as the prior
   security-fixes pass, deleted immediately after running.
4. **Exercised every changed endpoint with a real HTTP call against real
   data** rather than trusting the diff — this is what caught the `$11`
   parameter-type bug in the rewritten `payInvoice`; a code review alone
   would very plausibly have shipped it, since the query is syntactically
   valid SQL and the bug only manifests at Postgres's parameter-type-
   inference stage, not at parse time.
5. **Tested the exact real-world failure case end-to-end**, not just a
   synthetic minimal repro — the C-1 fix was verified against the *actual*
   stuck invoice from the original QA audit, through a full two-payment,
   mixed-payment-method collection sequence, confirming it reaches `'paid'`
   correctly and the ledger holds both entries.
6. **Verified negative cases, not just the happy path** — overpayment
   rejection (H-3), re-cancelling an already-cancelled visit (409, not a
   crash), a doctor session correctly forbidden from calling
   admin-only cancel endpoints (403).
7. **Ran `tsc -b` and a full backend module-load check after every batch
   of changes**, not just once at the end, to catch a broken import or
   type error close to when it was introduced rather than after dozens of
   further edits had piled on top.
8. **Chose not to chase H-6 to full resolution** once the remaining gap
   was confirmed dev-only with zero production impact and the effort
   curve for the remaining parent/child-remount case looked steep relative
   to its actual severity — documented the honest status instead of either
   overclaiming a full fix or silently leaving it unmentioned.
