# Full-Site QA Pass — 2026-07-24

## Scope & method

User asked for a full functional/UI QA pass across the running app — "every
little thing," with special emphasis on billing/invoicing logic — plus
product recommendations per role. This was done two ways in parallel:

1. **Live browser testing** (Puppeteer against the actual running dev
   stack, `localhost:3000` frontend / `localhost:5000` backend) — logged in
   as superadmin, admin, doctor, and patient in turn and clicked through
   real screens with real (if messy/demo) data already in the local `pdms`
   database.
2. **`code-griller` agent review** of the billing/invoicing backend in
   parallel (`billingController.js`, `visitsController.js`,
   `invoicesController.js`, `invoiceCalc.js`, `schema.sql`'s billing
   tables) — a static code read hunting specifically for money-correctness
   bugs, race conditions, and state-machine gaps.

Several findings from each side corroborated each other (e.g. the
partial-payment stuck-state bug was flagged by code review and then
reproduced live against 5 already-stuck invoices in the dev DB).

**Test accounts used** — existing dev/demo accounts had their passwords
reset to one shared value (`QaAudit#2026Test`) for this session, since no
plaintext credentials existed anywhere (by design): `superadmin`, `admin`,
`drmohamed` (doctor, richest existing data — 38 visits), `272003` (patient,
richest existing data — 14 visits/invoices). These are pre-existing fake
demo/test rows (names like "Test Patient Gaps", "QA Test Patient" already
in the table), not real PHI. If you use these accounts yourself, note the
password was changed.

## CRITICAL

### C-1. Partially-paid invoices get permanently stuck — no way to ever collect the rest
**Source:** code-griller, confirmed live against 5 real stuck invoices in the dev DB (incl. one with **4,398.75 SAR** outstanding).

Once an invoice takes a partial payment, `visit_invoices.status` becomes
`'partial'`. `BillVisitPage.tsx` only renders the payment form when
`status === 'pending_billing'` — so the moment an invoice is `'partial'`,
navigating to `/visits/:visitId/bill` shows **"This visit is not ready for
billing yet"** forever. There is no other screen anywhere in the app that
can collect a remaining balance. Reproduced live:
`/visits/3a24445f-ff58-4594-a9aa-24defce5163e/bill` → that exact
empty-state message, on an invoice sitting at 4,398.75 SAR outstanding.

Compounding bug if the gate is ever relaxed: `payInvoice`
(`billingController.js:481`) does `SET amount_paid = $9` — it **replaces**
the value, it does not add to it. A second collection attempt against the
same invoice overwrites (erases) the first payment rather than
accumulating, so even a fixed UI would under-report cash collected.

**Fix direction:** add a payment-ledger child table (one row per collection
event), derive `amount_paid` server-side as `SUM(ledger)`, and let the bill
screen operate on `status IN ('pending_billing', 'partial')`.

### C-2. VAT is hardcoded to 15% everywhere, ignoring the per-service `vat_pct` field
**Source:** code-griller. `billingController.js:253` — `calcItem({ ..., vat_pct: 15 })`, even though `clinic_services.vat_pct` is a real, independently-editable column (superadmin can set it via the Services page). Saudi VAT law zero-rates a lot of essential healthcare — any service deliberately configured at 0% VAT is silently overridden to 15%, over-charging the patient on every invoice using it.

**Fix:** `vat_pct: svc.rows[0]?.vat_pct ?? 15`.

## HIGH

### H-1. No row locking anywhere in billing — several concrete race conditions
**Source:** code-griller. Unlike `visitsController.create`/`appointmentsController` (which deliberately use `SERIALIZABLE` for exactly this reason), no billing write path locks anything:
- **Duplicate line items** — `addItem` checks for an existing `(invoice_id, service_id)` row with a plain `SELECT`, no `FOR UPDATE`, and there's no unique constraint either. Two near-simultaneous clicks → two rows instead of a merged qty.
- **Lost-update on invoice totals** — `refreshTotals` re-reads all items and overwrites the invoice's totals; two concurrent item edits on the same invoice can each overwrite the other's contribution.
- **Double payment processing** — `payInvoice` reads `visit_invoices` with a plain `SELECT`, no lock. Two concurrent `PATCH /pay` calls (double-submit is very plausible on a slow connection) both pass the status guard and both write — last write wins, silently.

**Fix:** `SELECT ... FOR UPDATE` on the invoice row at the top of every billing mutation; consider a unique constraint on `invoice_items(invoice_id, service_id)`.

### H-2. No cancel/void workflow for a visit or invoice created by mistake
**Source:** code-griller. The schema models `visit_invoices.status = 'cancelled'` but **no controller ever sets it** — grepped the whole backend. `visits.status` doesn't even have a `'cancelled'` value, and `visit_invoices.visit_id` is `ON DELETE RESTRICT`. A wrong-patient walk-in check-in, once created, can never be removed or voided — it sits in the billing worklist forever.

### H-3. Overpayment has no ceiling
**Source:** code-griller. `amount_paid` is validated only as `≥ 0`, no upper bound. Overpay and `amount_balance` goes negative, gets persisted, and prints raw on the invoice ("Balance: -50.00 SAR"). No refund/change tracking exists.

### H-4. Superadmin's own "Revenue Distribution by Department" bar can show over 100%
**Source:** live testing — reproduced on first login, showing **general (127%)**.

`billingController.js:793-812` (`getFinancialAnalytics`): the per-department
number sums `SUM(vi.grand_total)` for every `'paid'` **and** `'partial'`
invoice, then divides by `totalCollected`, which is `SUM(vi.amount_paid)`
for that same invoice set. For a `'partial'` invoice, `grand_total >
amount_paid` by definition — so the numerator (full billed amount) and
denominator (actual cash collected) are on two different bases, and the
percentage inflates past 100% the moment any partial payment exists in the
window (which, per C-1, is now permanent — every stuck partial invoice
keeps inflating this forever).

**Fix:** make the department breakdown sum `amount_paid` too, matching what
"Gross Revenue" above it already means.

### H-5. `medical_records.updated_at` is always NULL → displays as "Jan 1, 1970" everywhere
**Source:** live testing — every single row, on both the doctor's Medical Records list and the patient's own Medical Records tab, shows "Jan 1, 1970" in the Last Updated column.

Root cause confirmed by reading the schema and controller together:
`schema.sql:121` declares `updated_at TIMESTAMPTZ` with **no `DEFAULT`**,
and `medicalRecordsController.js` only ever *reads* `r.updated_at` (lines
99, 126, 182, 218) — no `INSERT`/`UPDATE` statement anywhere in that file
ever writes to it. Every row's `updated_at` is `NULL` in the DB → the
frontend's `formatDate(null)` → `new Date(null)` → the Unix epoch.

**Fix:** add `DEFAULT NOW()` to the column and set `updated_at = NOW()` in
the record-update statement (same pattern `departments.updated_at` already
uses correctly).

### H-6. A systemic frontend bug shows "Could not load X" on first paint across ~29 screens (dev-only, but real)
**Source:** live testing — reproduced 3× independently (Patient Profile → Appointments tab, Admin → Billing History, Patient → My Invoices), each time confirmed the **backend was completely healthy** (direct `curl` with the same session cookie returned 200 + correct data every time) while the browser's own request came back `status: 0` (aborted) and the page rendered a red "Could not load…" error.

**Root-caused conclusively:** temporarily removed `<StrictMode>` from
`main.tsx` (revert immediately after, no diff left behind) — with
StrictMode off, Billing History loaded correctly first try (SAR 506.00
collected, full invoice table). With it back on, the error reproduces every
time. React 18's StrictMode intentionally double-invokes effects in dev;
combined with this project's global React Query config
(`refetchOnMount: 'always'`, `retry: 1`, `staleTime: 0`, `main.tsx:11-18`),
the throwaway first mount's request appears to leak its
cancellation/rejection into the query's error state instead of being
silently superseded by the second (real) mount's request.

**This specific symptom will not appear in a production build** (StrictMode
only double-invokes in development), so it's not shipping-blocking as-is.
But 29 files share this `isLoading`/`isError` pattern
(`grep isError src/frontend/src/pages` → 29 matches), it makes local dev/QA
noisy and misleading (exactly what triggered this whole investigation), and
the underlying fragility — a query that can't gracefully absorb a
cancelled/aborted request — is a real code smell that could resurface in
production under different trigger conditions (flaky connection + fast
back-navigation, tab visibility changes, etc.), not just StrictMode.
Worth a real fix, not just "ignore it in dev."

## MEDIUM

### M-1. Insurance co-pay gets recomputed from scratch on every payment call
`billingController.js:462-476` — if a first payment establishes a co-pay split (e.g. 20 SAR patient share after 80% insurance coverage) and a follow-up payment call doesn't resend the insurance fields (natural when just collecting a leftover cash balance), `expectedPatientAmount` falls back to the **full grand_total**, silently discarding the coverage already applied. Currently unreachable only because of C-1's UI gate — fixing C-1 without also fixing this reintroduces an overcharge bug.

### M-2. `addItem`'s merge-on-existing path drops a resent `unit_price`
If a doctor adds more units of a service already on the invoice and the price legitimately changed, the second `unit_price` is silently ignored — no error, no indication.

### M-3. Financial report date filtering isn't Riyadh-anchored on the explicit-date path
`getFinancialAnalytics`'s "pick a specific date" branch and `getBillingHistory`'s `from`/`to` filters both do a naive `created_at::date` cast (DB session timezone — UTC in production) instead of the Riyadh-anchored pattern this codebase documents as mandatory elsewhere (`visitsController.js`'s `TODAY_START_SQL`). Picking a date near midnight will mis-bucket invoices by up to 3 hours. Separately, `getFinancialAnalytics` buckets by `created_at` while the cashier z-report (`getDailyReport`) buckets by `paid_at` — an invoice created one day and paid the next shows revenue on different days on the two screens.

### M-4. All currency math runs in JS floating point
`invoiceCalc.js`'s `round()` is the classic `Math.round(n*100)/100`, which isn't safe at exact half-cent boundaries. Given this feeds a printed Saudi Simplified Tax Invoice, worth moving to integer-cents or a decimal library, or doing the final roundingin SQL NUMERIC.

### M-5. Dashboard flow-pill photos are full-resolution (700KB–1.1MB PNGs) for 544×144 thumbnails
`real-waiting-area.png`/`real-reception.png`/`real-general-clinic.png` etc. are all uncompressed 1920×1080 PNGs, loaded at full size and scaled down in CSS. Observed one of them (`real-general-clinic.png`) fail to decode on first paint of the Admin Dashboard (broken-image icon), which cleared on reload — plausibly a decode/memory-pressure race from loading several 1MB+ images simultaneously. Resizing/compressing these to the actual display size would fix both the weight and likely the flakiness.

### M-6. Dashboards greet users by login username, not their real name
- Doctor dashboard: **"Good afternoon, Dr. drmohamed"** — should read "Dr. Mohamed Mousa" (or the Arabic name on file, "محمد موسي").
- Patient dashboard: **"Welcome, 272003"** / **"Welcome back, 272003"** — greeting a patient by their raw national ID number. Both dashboards already have the real name available server-side (it's shown elsewhere in the same session); the greeting alone falls back to `username`.

## LOW / polish

- **L-1.** `qty` has no upper bound in the billing route validators (`isInt({min:1})` only) — an absurd quantity can overflow `DECIMAL(10,2)` server-side and surfaces as a generic 500 instead of a clean 400.
- **L-2.** Invoice number sequence can gap under the addItem race in H-1 (`nextval()` isn't transactional) — normal Postgres behavior, but worth a note since this is a Saudi tax-invoice number specifically.
- **L-3.** Superadmin cannot apply discounts or collect payment (`PATCH /items/:itemId/discount` and `PATCH /pay` are admin-only, excluding superadmin, while `GET /` does include superadmin) — not a security gap, just possibly not intentional if superadmin is ever expected to fix a billing mistake directly.
- **L-4.** Two stale code comments (`billingController.js`, `visitsController.js`) assert `visits`/`visit_invoices` "have no RLS" — RLS was added to those tables in a later session (`schema.sql`, "HIGH-03" section) and is now enabled + forced. Not a bug (both layers currently agree), but a documentation trap for whoever edits the app-layer scoping logic next while trusting the stale comment.

## Product/feature recommendations (not bugs — your call on priority)

**Doctor**
- A doctor-scoped "recent lab results across my patients" view — flagged
  as a gap back in DELTA-022 (only a per-patient lookup exists today).
- "Pending Notes" on the doctor dashboard is a permanent `0` placeholder
  (no draft/incomplete concept in `medical_records` yet) — either build a
  real draft state or drop the stat card, a stat that can never move isn't
  useful.
- Prescription/medication history view (beyond "active prescriptions") —
  useful for repeat-visit patients on chronic medication.

**Admin/Staff**
- Fix C-1 first — this is the one that actually blocks staff from doing
  their job (collecting money owed).
- A real "list patients registered today" endpoint would let
  `RecentlyTreatedPatients`/`recentRegistrationsStore` stop relying on a
  client-side sessionStorage trail (see the earlier security-audit doc,
  Finding 4-B) and would survive a page refresh or a different terminal.
- **`clinic_rooms` + `RoomStatusGrid.tsx` already exist, fully built,
  seeded with 7 real rooms — and are wired into `api.ts` — but the
  component is never imported anywhere.** DELTA-022 deferred the room
  availability widget specifically because "no `rooms` table exists,"
  which is no longer true (or wasn't checked closely enough at the time).
  This looks like a near-free win — wire the existing component into the
  Staff/Doctor dashboard rather than building it from scratch.

**Patient**
- Appointment *reschedule*, not just cancel (UC-21 only covers
  cancellation today) — patients calling in to reschedule is a very
  common real-clinic workflow.
- Online invoice payment (even a simple "pay now" link) — right now a
  patient can *view* their invoice but has no way to actually pay it
  themselves.
- Family/dependent booking (book on behalf of a child or elderly parent)
  — common for a family clinic, and the self-registration design doc
  doesn't currently model it.

**Superadmin**
- Fix H-4 (the >100% bar) before anyone screenshots that dashboard for
  the report.
- Searchable/filterable audit log (currently a plain recent-activity
  feed) — valuable once there's more than a day of history.

**System-wide**
- The React Query config in `main.tsx` (H-6) is worth revisiting even
  though it's dev-only today — `refetchOnMount: 'always'` + `staleTime: 0`
  means literally every tab switch re-fetches everything, which is also
  just a lot of avoidable network traffic in production.
